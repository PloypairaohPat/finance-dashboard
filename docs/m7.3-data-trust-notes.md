## M7.3 first task — verify plan §7 against real data

**Do this before building any §7 fix.** Ground rule 1 below requires each §7 observation
to be checked against a known data source first. The M7.2 overnight run tried the one
source readable without production, the demo seed, and it can't do the job:

- **None of the four §7 observations reproduce from the demo seed** (numbers in
  *§7 re-verified against the demo seed*, near the end of this file).
- **The seed structurally cannot exhibit three of them, on any date.** It has no transfers,
  no pending transactions and no card or loan payments, and every demo budget card shows
  $0 spend. That rules out:
  - the income disagreement, which needs transfers to diverge;
  - the $288 budget figure, since budget spend is always $0;
  - the Monthly Spending climb, whose leading explanation is transfers and card payments
    counted as spend.

  The savings-rate blowup can't reproduce either, because demo income is never tiny, but
  that one depends on the seed's income amounts rather than on something missing from it.

So the verification has to come from somewhere else. **Two options, not yet decided:**

- **Read production carefully.** Check each observation against a named real account.
  This touches production data, so it needs an explicit method that fits the M7.0 rules
  (for example, the user reading figures in the browser, or a user-scoped read-only
  diagnostics endpoint), not an ad-hoc query.
- **Extend the seed.** Add what the demo lacks — transfers between the demo's own
  accounts, pending transactions, card payments, and budgets stored under display names —
  so each §7 mechanism can be reproduced locally and deterministically, and kept as a
  regression fixture.

The read-only script `backend/scripts/verify-s7-demo.ts` works against either: point it at
an extended seed, or reuse its per-figure breakdown as the checklist for a production read.

## Ground rules for M7.3 (decided during M7.1)

### 1. Re-verify every §7 observation before treating it as a bug

Plan §7 lists four number inconsistencies from screenshot review. At least one of
them does not match what the current code and demo seed can produce: §7 reports a
demo budget card showing **Food & Dining $288**, but the demo budgets can never show
spend (see *Demo budgets can never show spend* below).

So the four observations may not share a data source — some could be the demo, some
a real account, some production data that predates the current seed. **Re-check each
one against a known source before building a fix on it**: the local dev database
seeded by `prisma/seed-demo.ts` (`npm run db:dev:seed`), or a specific named account.
Re-checking four observations is cheaper than one fix built on a bad premise.

### 2. Expose silent failures before fixing the inputs that trigger them

Where a bad input and a swallowed error combine, fix the error handling first. Fixing
the input first hides the failure path instead of exposing it, and it stays broken
for the next input that reaches it.

## Budgets

### The category mismatch and the missing `res.ok` checks are one bug

- **Mismatch.** `frontend/src/AddBudgetRow.tsx` hardcodes its category list. It
  offers *Health & Fitness*, *Personal Care* and *Education*, which the backend
  rejects (`DISPLAY_CATEGORIES` in `backend/src/lib/categoryMap.ts`), and never offers
  *Housing*, *Subscriptions* or *Debt*, which the backend accepts. `GET
  /budgets/categories` already returns the real list; `TransactionList` and
  `TransactionDetail` use it.
- **Silent failure.** Neither budget write checks `res.ok`. A rejected category makes
  `upsertBudget` throw, `budgets.controller.ts` returns `500 { error: "Failed to save
  budget" }`, and `AddBudgetRow` still closes the form and reloads — the budget simply
  never appears. A failed limit edit in `BudgetCard` is equally silent.
- **Why they are one bug:** the mismatch is currently the only reliable way to reach
  the silent-failure path. Per ground rule 2, add the `res.ok` handling first; only
  then replace the hardcoded list with `GET /budgets/categories`.
- **The `res.ok` gap is probably not unique to budgets.** Audit every write in the
  app during M7.3, not just these two.

*Verified by reading* `AddBudgetRow.tsx`, `BudgetCard.tsx`, `categoryMap.ts`,
`budgets.service.ts` and `budgets.controller.ts`. *Not yet reproduced in a browser.*

### Demo budgets can never show spend

`prisma/seed-demo.ts` seeds the demo budgets under Plaid category codes (`GROCERIES`,
`FOOD_AND_DRINK`, `TRANSPORTATION`, `GENERAL_MERCHANDISE`, `ENTERTAINMENT`).
`fetchBudgetsWithSpend` in `budgets.service.ts` sums spend under *display* names
(`mapPlaidCategory` → "Food & Dining", …) and looks each budget up by its own category
string, so a budget stored as `FOOD_AND_DRINK` never matches and always reports $0.

This **contradicts plan §7's** "Food & Dining $288 (budget card)" observation of the
live demo — see ground rule 1.

*Verified by reading* `seed-demo.ts` and `budgets.service.ts`. *Not yet checked against
the local dev database or production.*

## Writes

### Blocked demo writes read as success (named bug pattern)

**The pattern.** In demo mode the backend's `demoReadOnly` middleware
(`backend/src/middleware/auth.ts`) answers **every** non-GET request with
`200 { demo: true, ok: false, message: "Demo mode — changes aren't saved…" }`.
`backend/tests/isolation.test.ts` asserts that exact shape. Because the status is 200,
`res.ok` is `true`, so a write that checks only `res.ok` treats a blocked demo write as
saved. So does a write that checks only `data.error`, or checks nothing at all.

**Known fix.** Read every write's response through `readWriteResult` in
`frontend/src/lib/writeResult.ts` (added in M7.1 stage 3). It treats a `demo` /
`ok: false` body as a failure even on HTTP 200, then a non-2xx status, then a 2xx
`error` body. Show its `message` to the user, and only update local state after
`ok: true`.

**How to reproduce any row below.** Open the app with `?demo=1`, perform the action,
and watch the Network tab: the response is `200 {"demo":true,"ok":false,…}` while the
UI behaves as if it saved.

## Alerts

Found while building the M7.1 stage 3 bell. Not fixed there unless marked.

### Alerts never resolve (named bug)

**This is the actual fix for plan §7's alert overload ("91 active" / "Show 89 more").**
The M7.1 stage 3 bell is presentation only: it caps how many alerts are *shown*, not how
many are *active*, and the count on the bell is still the unbounded number.

**The bug.** Detectors only ever create or update rows (`runDetectors` in
`backend/src/services/alerts/dispatcher.ts` upserts by `userId + fingerprint`). Nothing
in the backend deletes, resolves, expires or soft-deletes an alert, so no code path ever
sets `deletedAt` on an alert, and `dismissedAt` is only set by the user. "Active" means
`deletedAt IS NULL AND dismissedAt IS NULL`. So once a detector fires, its row stays
active until the user dismisses it, **whether or not the condition still holds**.

**Why the count grows without bound.** Every fingerprint embeds either a date, a
transaction id or a month, so every new day, transaction or month creates a *new* row
alongside the old ones. Nothing ever removes the old ones. Which detectors leak:

| Detector | Fingerprint | Rows it leaves active |
|---|---|---|
| `lowBalance` | `low_balance:${account.id}:${date}` | **One per account per day** under $100, forever. A month under $100 is ~30 rows per account, and they stay after the balance recovers. |
| `largeTransaction` | `large_tx:${tx.id}` | **One per large transaction.** The detector only looks back 14 days, but rows older than that never leave. |
| `budgetStatus` (exceeded) | `budget_exceeded:${category}:${ym}` | One per category per month, still active in later months |
| `budgetStatus` (projected) | `budget_proj:${category}:${ym}` | One per category per month; stays even after the month ends or the projection drops back under |
| `overspending` | `spending_vs_avg:${cat}:${ym}` | One per category per month |
| `subscriptionPriceUp` | `price_up:${merchantName}:${ym}` | One per merchant per month |
| `missedPaycheck` | `missed_paycheck:${ym}` | One per month, stays after the paycheck arrives |
| `positiveMilestones` | `milestone:{savings_rate_high, spending_down_mom, runway_6mo}:${ym}` | Up to three per month; last month's "good news" stays active |

Daily and per-transaction rows dominate. A single account that sits under $100 for three
months contributes ~90 active alerts on its own, the same order as §7's "91 active".
*That arithmetic is illustrative: the 91 has not been traced to specific rows.*

**Sync feeds the wall.** Since M7.1 stage 4, every Sync re-fetches every mounted view.
On Overview that is `POST /sync` plus about 15 GETs, and one of them is `GET /alerts`.
So each Sync runs the 8 detectors at least twice:
- once per Plaid item inside the sync itself (`plaidSync.ts` calls `runDetectors`
  after syncing each item), and
- once more for `GET /alerts`.

Every detector run upserts. Re-running on the same day with no new data doesn't add
rows, because the fingerprints match. But the sync is exactly what brings in new
transactions (new `large_tx` rows) and, on a new day or month, new `low_balance` and
monthly rows. None of those ever leave. So repeated Syncs, and every page load that
fetches `/alerts`, keep growing the wall.

This isn't new with stage 4: Sync already triggered the detectors in the sync and
re-fetched `/alerts` before M7.1. Stage 4 makes Sync available on every route, so it
will run more often. It connects the two findings: the Sync fan-out is a steady
source of detector runs, and "never resolve" is why each run can only add rows.

**Why this reframes the reopen question.** M7.1 stage 3 found that a dismissal lasts only
until the fingerprint's period ends (see *Dismissals were undone by the next GET
/alerts*), and that a condition which clears and re-fires within the same period stays
dismissed. That looked like it needed a reopen policy. It doesn't, or at least not yet:
once alerts resolve when their condition lapses, a re-fired condition is simply a **new
alert**, and "should a dismissed alert reopen?" largely dissolves. Designing a reopen
policy on top of a system where nothing resolves would be solving the wrong problem, so
none was built.

**What a fix has to decide in M7.3** (not decided here): whether `runDetectors` resolves
active alerts that were not produced in the current run, and for which kinds (a
`large_tx` alert is about an event, not an ongoing condition, so "the condition lapsed"
may mean "older than the lookback"); whether resolution is a soft delete or its own
state; and whether per-day fingerprints like `low_balance` should become per-condition
(one row while the balance stays low) so one episode is one alert.

*Verified by reading `dispatcher.ts`, every detector's fingerprint, and a repo-wide
search showing no code deletes, resolves or expires alerts (the only alert deletes are
in `prisma/seed-demo.ts` and the test suite). Not reproduced against real data.*

### Dismissals were undone by the next GET /alerts

**Fixed in M7.1 stage 3.** `runDetectors`' upsert update branch set `dismissedAt: null`,
and GET /alerts runs the detectors before every read, so any dismissed alert whose
condition still held came back on the next page load. The reset is removed.
Reproduced (fails before, passes after) by `backend/tests/alerts-dismissal.test.ts`.

**Accepted limitation.** A dismissal now lasts for its fingerprint's period, not for the
condition. Dismissing today's `low_balance` alert holds until the next day, even if the
balance falls further and the severity goes from medium to high. Dismissing a monthly
alert holds for the rest of that month. Accepted for now: see *Alerts never resolve*, which
is where that question actually belongs.

### GET /alerts writes, including for the demo user

Because GET /alerts runs detectors and upserts, a read writes rows. `demoReadOnly` only
blocks non-GET methods, so demo visitors' reads upsert alert rows under `demo-user`.

### Smaller

- The demo seed's three alerts use `kind` values (`budget_pace`, `new_merchant`) that
  aren't in the frontend's `AlertKind` type, and fingerprints (`demo-*`) no detector
  produces.
- `GET /alerts/all` (`fetchAllAlerts`) has no caller in the frontend.

## §7 re-verified against the demo seed (M7.2 overnight run)

Ground rule 1 applied to all four plan §7 observations, against the one data source
that can be read without touching production: the deterministic demo seed.

**How.** `backend/scripts/verify-s7-demo.ts`, read-only. It computes each figure with the
app's own services and alert detectors; the detectors are called as pure functions, so
nothing is upserted. It refuses any non-local `DATABASE_URL`.

```bash
cd backend
npm run db:dev:seed
npm run db:guard && npx dotenv -e .env.dev -- tsx scripts/verify-s7-demo.ts
```

**Data it ran on (2026-09-15, local dev DB seeded the same day).** 145 transactions,
May 1 – Sep 15 2026. **0 pending, 0 transfers, 0 loan or card payments.** Income is two
paychecks of $2,400–$2,500, on the 1st and the 15th. The 5 budgets are stored under Plaid
codes.

**Caveat.** The seed's random amounts are deterministic, but its dates are relative to the
day it runs and the current month is cut off at today. Exact dollar figures therefore
differ by seed date. Whether a figure *can* appear does not.

top of this file, with the two options (read production carefully, or extend the seed).

**One pattern worth testing on real data.** For the same month, the overspending
detector's "$313" and Month over month's "$313.33" are computed the same way whenever
there are no pending transactions, no internal transfers and no dining merchant counted as
a subscription. So they are plausibly **the same number, rounded**. The budget card is the
odd one out: it excludes pending transactions (`pending: false`) and the other two don't.
A hypothesis for a real account is therefore about $25.33 of *pending* dining transactions
that month. *Unverified.*
