# M7.3 — data trust notes

Findings captured during M7.1 (the tab refactor) and deliberately **not fixed** there,
so M7.3 can treat data trust as one consistent pass instead of scattered patches.
Every entry says how it was verified. Anything not verified says so.

## Ground rules for M7.3 (decided during M7.1)

### 1. Re-verify every §7 observation before treating it as a bug

Plan §7 lists four number inconsistencies from screenshot review. At least one of
them does not match what the current code and demo seed can produce: §7 reports a
demo budget card showing **Food & Dining $288**, but the demo budgets can never show
spend (see *Demo budgets can never show spend* below).

So the four observations may not share a data source — some could be the demo, some
a real account, some production data that predates the current seed. **Re-check each
one against a known source before building a fix on it**: the local dev database
seeded by `prisma/seed-demo.ts` (`npm run db:dev:seed`), or a specific named account.
Re-checking four observations is cheaper than one fix built on a bad premise.

### 2. Expose silent failures before fixing the inputs that trigger them

Where a bad input and a swallowed error combine, fix the error handling first. Fixing
the input first hides the failure path instead of exposing it, and it stays broken
for the next input that reaches it.

## Budgets

### The category mismatch and the missing `res.ok` checks are one bug

- **Mismatch.** `frontend/src/AddBudgetRow.tsx` hardcodes its category list. It
  offers *Health & Fitness*, *Personal Care* and *Education*, which the backend
  rejects (`DISPLAY_CATEGORIES` in `backend/src/lib/categoryMap.ts`), and never offers
  *Housing*, *Subscriptions* or *Debt*, which the backend accepts. `GET
  /budgets/categories` already returns the real list; `TransactionList` and
  `TransactionDetail` use it.
- **Silent failure.** Neither budget write checks `res.ok`. A rejected category makes
  `upsertBudget` throw, `budgets.controller.ts` returns `500 { error: "Failed to save
  budget" }`, and `AddBudgetRow` still closes the form and reloads — the budget simply
  never appears. A failed limit edit in `BudgetCard` is equally silent.
- **Why they are one bug:** the mismatch is currently the only reliable way to reach
  the silent-failure path. Per ground rule 2, add the `res.ok` handling first; only
  then replace the hardcoded list with `GET /budgets/categories`.
- **The `res.ok` gap is probably not unique to budgets.** Audit every write in the
  app during M7.3, not just these two.

*Verified by reading* `AddBudgetRow.tsx`, `BudgetCard.tsx`, `categoryMap.ts`,
`budgets.service.ts` and `budgets.controller.ts`. *Not yet reproduced in a browser.*

### Demo budgets can never show spend

`prisma/seed-demo.ts` seeds the demo budgets under Plaid category codes (`GROCERIES`,
`FOOD_AND_DRINK`, `TRANSPORTATION`, `GENERAL_MERCHANDISE`, `ENTERTAINMENT`).
`fetchBudgetsWithSpend` in `budgets.service.ts` sums spend under *display* names
(`mapPlaidCategory` → "Food & Dining", …) and looks each budget up by its own category
string, so a budget stored as `FOOD_AND_DRINK` never matches and always reports $0.

This **contradicts plan §7's** "Food & Dining $288 (budget card)" observation of the
live demo — see ground rule 1.

*Verified by reading* `seed-demo.ts` and `budgets.service.ts`. *Not yet checked against
the local dev database or production.*

## Overview

Everything in this section comes from **reading the code only**. Nothing has been
reproduced against a known data source. Per ground rule 1, each entry is a *candidate*
explanation for a §7 observation, not a confirmed cause.

### At least three definitions of "spend" and two of "income" feed one page

| Widget | Endpoint → service | Pending | Internal transfers | Spend = | Income = |
|---|---|---|---|---|---|
| Hero "Saved this month", InsightsDashboard | `/insights` → `fetchInsights` | included | filtered (`filterInternalTransfers`) | amount > 0 **and** `isSpending` | \|amount\| where amount < 0 |
| Month over month (`CategoryComparison`) | `/categories/comparison` → `fetchCategorySpend` | included | filtered | `isSpending`, with subscription merchants in their own bucket | — |
| Monthly Spending (`TrendChart`) | `/transactions/trends` → `fetchMonthlyTotals` | **excluded** | **not filtered** | every amount > 0 | — |
| Cash flow, Monthly savings | `/cashflow` → `cashflow.service` | **excluded** | **not filtered** | every amount > 0 | \|amount\| where amount < 0 |
| Budget cards (Budgets tab) | `/budgets` → `fetchBudgetsWithSpend` | **excluded** | **not filtered** | per display category | — |

Candidate explanations for plan §7, **all unverified**:

- **Income $50 vs $550.** `/insights` drops transfers between the user's own accounts;
  `/cashflow` counts them as income. The windows also differ: `/insights` covers the
  current calendar month, `/cashflow` six months.
- **Monthly Spending climbing to about $16k.** `TrendChart` plots per-month totals, not a
  running total, so the chart itself is labelled correctly. But `fetchMonthlyTotals`
  sums every settled positive amount with no `isSpending` or transfer filter, so card
  payments, loan payments and transfers out plausibly count as spend.
- **Food & Dining $313.33 (Month over month) vs $288 (budget card).** The two differ on
  pending handling and on transfer filtering, so a gap is expected even from identical
  data. But the demo seed cannot produce *any* budget spend (see *Demo budgets can never
  show spend*), so this pair cannot both have come from the current demo. This is the
  clearest case for ground rule 1.

### Savings rate is unclamped

`fetchInsights` computes `savingsRate = netSaved / income * 100` with no floor and no
minimum-income guard. A month with tiny positive income produces rates like §7's
−8431.6%. Decide in M7.3 whether to clamp it, hide it below an income threshold, or show
"—".

*Verified by reading* `insights.service.ts`. *Not reproduced.*

### `/insights` is fetched twice on Overview

App's `fetchInsightsSummary` fetches `/insights` for the hero's "Saved this month", and
`InsightsDashboard` fetches it again for its own cards. The two can't disagree today
because they share a source, but it's a wasted request, and it's a place where the two
could drift apart if either call ever gains parameters (M7.2's period anchor).

*Verified by reading* `App.tsx` and `InsightsDashboard.tsx`.

### Largest purchases is left inside InsightsDashboard

`largestPurchases` comes back in the same `/insights` response and is rendered by
`InsightsDashboard`. It was **not** split out during M7.1: moving it would need a second
fetch or an endpoint split, and plan §7 already proposes merging *Top merchants* and
*Largest purchases* in M7.3, so any restructure belongs there.

### Overview's child widgets are not refreshed by Sync

`InsightsDashboard`, `CategoryComparison`, `TrendChart`, `CashFlowChart`,
`SavingsTrend`, `NetWorthChart`, `WeeklyDigestCard`, `AlertCenter`,
`FinancialScoreCard` and `GoalsCard` all fetch for themselves, so App's Sync button
doesn't reach them. That predates M7.1. It is tracked with the M7.1 stage 4 refresh
work (`TODO(M7.1-stage4-sync-refresh)`), not here, but it matters when re-verifying §7:
after pressing Sync, the hero and Spending breakdown can show fresh data while the
widgets below still show what they loaded on mount. *Inferred from reading; each
widget's re-fetch triggers have not been checked one by one.*
