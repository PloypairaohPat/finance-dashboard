# Taxonomy and identity audit

`fix/dead-detectors` found two detectors keyed on values real data never has: a field
that didn't exist (`incomeStreams`) and an income code from the wrong taxonomy generation
(`INCOME_WAGES`). This audit asked whether that class of bug runs wider, in two places:
the category codes the classifier keys on, and how we tell one payer or merchant from
another. It is read-only. **No classifier change comes out of it.**

All of it was measured with read-only scripts, run against production by the owner,
printing counts, Plaid enum values and yes/no only. They are in `backend/scripts/`:
`taxonomy-audit.ts`, `rent-and-pay-audit.ts` and `card-and-identity-checks.ts`. What
follows is conclusions; per-user figures stayed in the terminal.

## Our Items return Plaid's PFCv2 taxonomy

Established from Plaid's documentation and our client, not from samples. Plaid:
customers who enabled Transactions before 3 December 2025 receive v1 by default and may
opt in to v2; those who enabled it on or after that date receive only v2. Ledger enabled
it after that date. Our SDK (plaid-node 24.0.0) predates the version option,
and no call we make requests a version, so we get the account's default: v2. Production
data agrees: it carries codes that exist only in v2 (`INCOME_SALARY`, `OTHER_OTHER`, the
`*_FROM_APPS` transfer codes).

Every detailed code `src/` and the demo reference was checked against Plaid's combined
v1/v2 taxonomy file:

- **All but two are valid, unchanged v2 codes.**
- **`RENT_AND_UTILITIES_UTILITIES`** (a `categoryMap` prefix) exists in neither taxonomy.
  It was harmless — the `RENT_AND_UTILITIES` prefix maps the same rows to the same
  bucket — and is removed.
- **`INCOME_OTHER_INCOME`**, used only by the demo, is the v1 name; v2 calls it
  `INCOME_OTHER`. The demo was exercising a code production cannot send. Renamed; the
  primary is the same, so no verdict changes.

**R7's savings branch is keyed on real codes.** `TRANSFER_OUT_SAVINGS`,
`TRANSFER_IN_SAVINGS` and the two `*_INVESTMENT_AND_RETIREMENT_FUNDS` codes are current
v2 codes. They had looked like the `incomeStreams` class because neither real user has
produced them, so the savings branch has never fired on real data. That is an absence in
the data, not a mistake in the rule. Nothing to fix; the demo is where the branch is
exercised.

## Transfers that count as spending

Transfers out whose other leg Ledger can't see, and which carry no code the classifier
excludes, count as ordinary spending. On real data they are **immaterial** — a small
fraction of any period's spend — so nothing changes. Cash withdrawals counting as
spending stays intended; the user-facing doc already says so.

## Card payments

Two shapes looked wrong and are not:

- **Income-coded inflows on a credit account, paired as card payments.** Plaid codes
  the card side of a card payment inconsistently; the demo carries fixtures for it.
  These are that leg, correctly paired.
- **Card payments counted as spending (R5, D3).** A payment to an institution where no
  card is linked, with no matching card-side inflow, is a payment to a card Ledger can't
  see. Counting it is D3 by design: it is the only evidence of that card's spending.

## Identity

**Payers.** Income deposits carry no Plaid entity id, so there is no id to group payers
by. Identifying a payer waits for M7.6's stored inflow streams.

**Merchants.** On spend, Plaid's ids behave differently by where they come from:

- **`merchant_entity_id`** merges look-alike names of one merchant — the description
  variants that subscription detection's normalised name keeps apart.
- **A counterparty's `entity_id`** depends on the counterparty's type. On a
  `payment_app`, `payment_terminal` or `marketplace` counterparty it identifies the rail,
  not the payee, so keying on it merges unrelated payees or merchants.

## What else this found

**A measurement mistake, and the rule it gave.** The first versions of two scripts
understated spend in some periods. They classified "first transaction to now", and
`classifyWindow` — correctly — reports the payment-app cap only for periods it covered
end to end, so Payments to people fell out of the first and current periods. The scripts
now take spend from `fetchCashFlow`, the code behind `GET /cashflow`, and print whether
their parts add back to it; every period reconciles. **A script that reports a figure the
app shows must take it from the endpoint's code, not recompute it.** `verify-figures.ts`
already worked that way.

## Carried items

- **Payer identity waits for M7.6** (above), alongside the missed-paycheck notes already
  in `m7.3-consumer-audit.md`.
- **Entity ids live only in `rawJson`, and `rawJson` is written when a row is created,
  never on update.** A key built on them needs real columns, filled on create and update,
  and backfilled. That belongs to the manual-subscriptions work.
- **`rawJson` stores Plaid's full transaction payload** — everything Plaid sends, not just
  what Ledger uses. What is kept, why, and for how long belongs in M7.7's data-handling
  document.
