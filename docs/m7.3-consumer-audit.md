# Who decides what a transaction means — the full inventory

M7.3's conversion list came from plan §7's list of *symptoms*: the four screens where
numbers visibly disagreed. That was never the same thing as the list of *consumers* —
the places in the code that decide, on their own, what counts as spending, income or a
transfer. This is the consumer list, found by sweep rather than by memory.

**How it was found.** Grep across `backend/src`, `backend/scripts` and `frontend/src` for:
the old two-tier filter (`filterInternalTransfers`), the category helpers (`isSpending`,
`mapPlaidCategory`, `labelForPrimary`), raw sign logic (`amount > 0`, `amount < 0`,
`amount: { gt: 0 }`, `{ lt: 0 }`), direct Plaid category-string tests (`TRANSFER_`,
`INCOME_`, `LOAN_PAYMENTS`), and `pending: false` filters.

**Result at the time of writing:** five files use `lib/classifier.ts`. Twelve live
consumers do not, plus one dead file and one one-off script.

## What each disagreement actually does

**1. Score.** The savings-rate component treats every negative amount as income —
payment-app repayments, refunds, and the transfers the old filter misses (calibration:
30 of 48 transfer-shaped pairs). The debt-load component does the same with **no**
transfer filter at all, then divides debt by it. The output is a single authoritative
number, which makes it the worst place in the app to be wrong.

**2. Goals.** Average monthly expenses drive the emergency-fund target. Transfers and
card payments inflate it, so the target is too high and "months of runway" reads low.

**3. Digest.** Counts refunds and transfers in as income, card payments as spending, for
a weekly figure someone reads at a glance.

**4–8. Detectors.** All five files decide independently. Two consequences worth calling
out:

- Budget alerts now describe a **different window** from the budget cards they refer to.
  The cards moved to money periods in M7.3; the detector still uses calendar months. For
  anyone whose period does not start on the 1st, a card can read "on track" while the
  alert says "over budget". This inconsistency was *introduced* by converting one side.
- `largeTransaction` has no category test at all, so a card payment or a transfer to
  savings fires "Large purchase detected" — the alert most likely to make someone
  distrust the app.

**9. Subscriptions.** Any repeating positive amount can become a "bill", including a
monthly savings transfer or a card payment. It also now disagrees with the spending
breakdown, which stopped applying the subscription-bucket override during M7.3 (visible
in the reconciliation report as `subscription-override-dropped`).

**12. Frontend.** Sign drives colour and sign character only — no totals are computed
client-side. But once a card payment renders red as `−$812.34` while every total says it
is not spending, the row and the total are telling the user different things. That is
§7's original problem in a new place, not a cosmetic detail.

## Not consumers

- `services/networth.service.ts` — balance snapshots; reads no transactions.
- `services/activity.service.ts` — first-transaction date; any row counts, which is right.
- `services/plaidSync.ts`, `services/cleaner.ts` — write side; they record Plaid's
  categories rather than interpreting them.
- `scripts/migrate-budget-categories.ts` — maps budget *labels*, not transactions.

## Dead code

`services/alerts.service.ts` — roughly 160 lines carrying its own spend definitions,
referenced from nowhere. Superseded by `alerts/detectors/*`. To be deleted, not converted.

## A separate bug found on the way: local-time month keys

`score.service.ts` and `goals.service.ts` build month keys with `getFullYear()` and
`getMonth()` — **local time**, while `lib/period.ts`, the stored transaction dates and
the rest of the codebase are UTC throughout. A sweep for this pattern across the backend
found it is not confined to those two:

| File | What is bucketed in local time |
|---|---|
| `alerts/detectors/budgetStatus.ts` | `ym` key, day-of-month, days-in-month |
| `alerts/detectors/overspending.ts` | `ym` key for both the current month and each prior month |
| `alerts/detectors/positiveMilestones.ts` | `ym` key, and `Date.UTC(now.getFullYear(), …)` — **local** year/month fed into a **UTC** constructor |
| `alerts/detectors/missedPaycheck.ts` | `ym` key |
| `alerts/detectors/subscriptionPriceUp.ts` | `ym` key (fingerprint only) |
| `services/score.service.ts` | `ym` key and two "months covered" divisors |
| `services/goals.service.ts` | "months of data" divisor |
| `services/recurring.service.ts` | next-occurrence date arithmetic |

`positiveMilestones` is the clearest: it reads the year and month in local time and
builds a UTC date from them, so near a month boundary the window and the label can
disagree by a month.

**Not in this class:** the many `setDate(getDate() - N)` patterns (90-day lookbacks,
the detector context window, `pendingResolver`). Those are durations rather than
bucketing, and are only off across a DST transition on a non-UTC host.

Converting a consumer to the classifier removes its month-key bug as a side effect,
because the classifier works in money periods via `periodKeyOf`, which is UTC. The files
that are *not* being converted still need the fix on its own.

## Why this list outlives M7.3

M7.6 replaces the recurring and subscription machinery, and M7.5 adds card-cycle
budgets. Both need to know which parts of the app still hold private opinions about what
a transaction means. That is what this file is for: the conversion order below is a
snapshot, but the inventory is the map.
