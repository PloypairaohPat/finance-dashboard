# Who decides what a transaction means — the full inventory

M7.3's conversion list came from plan §7's list of *symptoms*: the four screens where
numbers visibly disagreed. That was never the same thing as the list of *consumers* —
the places in the code that decide, on their own, what counts as spending, income or a
transfer. This is the consumer list, found by sweep rather than by memory.

**How it was found.** Grep across `backend/src`, `backend/scripts` and `frontend/src` for:
the old two-tier filter (`filterInternalTransfers`), the category helpers (`isSpending`,
`mapPlaidCategory`, `labelForPrimary`), raw sign logic (`amount > 0`, `amount < 0`,
`amount: { gt: 0 }`, `{ lt: 0 }`), direct Plaid category-string tests (`TRANSFER_`,
`INCOME_`, `LOAN_PAYMENTS`), and `pending: false` filters.

**Result at the time of writing:** five files use `lib/classifier.ts`. Twelve live
consumers do not, plus one dead file and one one-off script.

## What each disagreement actually does

**1. Score.** The savings-rate component treats every negative amount as income —
payment-app repayments, refunds, and the transfers the old filter misses (calibration:
30 of 48 transfer-shaped pairs). The debt-load component does the same with **no**
transfer filter at all, then divides debt by it. The output is a single authoritative
number, which makes it the worst place in the app to be wrong.

**2. Goals.** Average monthly expenses drive the emergency-fund target. Transfers and
card payments inflate it, so the target is too high and "months of runway" reads low.

**3. Digest.** Counts refunds and transfers in as income, card payments as spending, for
a weekly figure someone reads at a glance.

**4–8. Detectors.** All five files decide independently. Two consequences worth calling
out:

- Budget alerts now describe a **different window** from the budget cards they refer to.
  The cards moved to money periods in M7.3; the detector still uses calendar months. For
  anyone whose period does not start on the 1st, a card can read "on track" while the
  alert says "over budget". This inconsistency was *introduced* by converting one side.
- `largeTransaction` has no category test at all, so a card payment or a transfer to
  savings fires "Large purchase detected" — the alert most likely to make someone
  distrust the app.

**9. Subscriptions.** Any repeating positive amount can become a "bill", including a
monthly savings transfer or a card payment. It also now disagrees with the spending
breakdown, which stopped applying the subscription-bucket override during M7.3 (visible
in the reconciliation report as `subscription-override-dropped`).

**12. Frontend.** Sign drives colour and sign character only — no totals are computed
client-side. But once a card payment renders red as `−$812.34` while every total says it
is not spending, the row and the total are telling the user different things. That is
§7's original problem in a new place, not a cosmetic detail.

## Found later: a writer that corrupts what the classifier reads

The sweep looked for code that *interprets* transactions. It missed code that *rewrites* the
fields interpretation depends on, and there is one:

**`TransactionDetail.tsx` → `PATCH /transactions/:id` → `updateTransaction`.** The detail
panel's category dropdown offers **display** categories ("Shopping", "Debt"), and
`updateTransaction` writes the chosen value straight into `categoryPrimary` — the field
that holds Plaid codes (`GENERAL_MERCHANDISE`, `LOAN_PAYMENTS`). Consequences:

- `mapPlaidCategory("Shopping")` matches no prefix, so a purchase recategorised *to*
  Shopping is counted under **Other** in every total.
- Recategorising a transfer replaces its `TRANSFER_*` code, which removes the transfer
  signal R2 pairs on — so an internal transfer can silently become spending.
- The panel's dropdown also opens pre-selected on the first option ("Housing") for any row
  whose Plaid label is not a display category, which invites exactly that edit.

Pre-existing (M5.7), not introduced by M7.3. **Fixed in M7.3** (the category-save fix):

- A display category is now stored as Plaid codes that map back to it
  (`ASSIGNABLE_CATEGORY_CODES` in `lib/categoryMap.ts`) — each primary's generic
  `*_OTHER_*` detailed code, and no code at all for *Other*. A test asserts every one
  round-trips through `mapPlaidCategory` and names no transfer, card-payment, savings or
  income code. *Subscriptions* is not assignable: no Plaid code maps to it.
- `PATCH /transactions/:id` returns 400 for a name outside that list, and 409 for a row
  whose category decides nothing (`canRecategorise` in `lib/classifier.ts`: only R7
  ordinary spend and netted R3 refunds, and never a row still carrying a `TRANSFER_*`
  code). So a transfer or card payment can no longer be turned into spending from the
  panel. The panel shows those rows' category read-only.
- The panel opens on the row's `displayCategory` rather than Plaid's badge label, and the
  PATCH response is the re-enriched row, verdict included.

What this does **not** settle, still open for a later design: whether an override should
be stored separately from Plaid's code (today a later Plaid sync of a *modified*
transaction overwrites the user's choice), and whether a user may override a verdict.
Rows saved with a display name before the fix are still counted under *Other* until
repaired: `docs/m7.3-category-repair.md` has a counts-only query and a proposed repair, neither run.

### The gap the fix leaves: a verdict can't be appealed

The 409 lock is deliberate: a category edit must never silently turn a transfer or a card
payment into spending. But it means that **nothing a user can do in the app changes a
classifier verdict.** If a row is misjudged, the user can see the chip saying so and has
no way to correct it.

The rows most likely to be misjudged are among the locked ones. Payment-app inflows
(R4, "Repayment") are decided by counterparty alone: any money in through a payment app,
with no merchant behind it, is treated as someone paying the user back. Venmo income for
freelance work, rent from a roommate or a sale on Marketplace all look identical to the
rules, so they come out as repayments, and those rows are locked. The same holds for unidentified inflows,
single-leg transfers, and card payments to an unlinked card.

The eventual fix is **not** a category edit. It is a verdict-level override ("this was
income", "this was a transfer between my accounts"), stored separately from Plaid's
codes and applied by the classifier as an input that outranks its rules. That needs its
own decisions: which verdicts are appealable, whether an override on one leg of a pair
releases the other, how it survives a Plaid sync, and how it shows in the
reconciliation. It is its own milestone, not a follow-up to this fix.

## Not consumers

- `services/networth.service.ts` — balance snapshots; reads no transactions.
- `services/activity.service.ts` — first-transaction date; any row counts, which is right.
- `services/plaidSync.ts`, `services/cleaner.ts` — write side; they record Plaid's
  categories rather than interpreting them.
- `scripts/migrate-budget-categories.ts` — maps budget *labels*, not transactions.

## Dead code

`services/alerts.service.ts` — roughly 160 lines carrying its own spend definitions,
referenced from nowhere. Superseded by `alerts/detectors/*`. To be deleted, not converted.

## A separate bug found on the way: local-time month keys

`score.service.ts` and `goals.service.ts` build month keys with `getFullYear()` and
`getMonth()` — **local time**, while `lib/period.ts`, the stored transaction dates and
the rest of the codebase are UTC throughout. A sweep for this pattern across the backend
found it is not confined to those two:

| File | What is bucketed in local time |
|---|---|
| `alerts/detectors/budgetStatus.ts` | `ym` key, day-of-month, days-in-month |
| `alerts/detectors/overspending.ts` | `ym` key for both the current month and each prior month |
| `alerts/detectors/positiveMilestones.ts` | `ym` key, and `Date.UTC(now.getFullYear(), …)` — **local** year/month fed into a **UTC** constructor |
| `alerts/detectors/missedPaycheck.ts` | `ym` key |
| `alerts/detectors/subscriptionPriceUp.ts` | `ym` key (fingerprint only) |
| `services/score.service.ts` | `ym` key and two "months covered" divisors |
| `services/goals.service.ts` | "months of data" divisor |
| `services/recurring.service.ts` | next-occurrence date arithmetic |

`positiveMilestones` is the clearest: it reads the year and month in local time and
builds a UTC date from them, so near a month boundary the window and the label can
disagree by a month.

**Not in this class:** the many `setDate(getDate() - N)` patterns (90-day lookbacks,
the detector context window, `pendingResolver`). Those are durations rather than
bucketing, and are only off across a DST transition on a non-UTC host.

Converting a consumer to the classifier removes its month-key bug as a side effect,
because the classifier works in money periods via `periodKeyOf`, which is UTC. The files
that are *not* being converted still need the fix on its own.

### Known remainders

After the M7.3 conversions, six of the eight are fixed. Two are left, deliberately, and a
third was found by the check below:

- **`alerts/detectors/subscriptionPriceUp.ts`** — its `ym` is built from local-time
  `getFullYear()`/`getMonth()` and used **only in the alert fingerprint**. Railway runs in
  UTC, so in production it is inert today. It is recorded rather than dismissed because
  local development now exists: on a machine east or west of UTC, a price-change alert
  raised near a month boundary gets a fingerprint for a different month than production
  would give it. That is the same latent class as the mixed-clocks finding from M7.2 —
  two parts of the system disagreeing about which month it is — and the fix is one line
  when this detector is next touched.
- **`services/recurring.service.ts`** — next-occurrence arithmetic in local time. Left
  alone: M7.6 replaces this service with Plaid Recurring Transactions.
- **`services/subscriptions.service.ts` → `predictNextCharge`** — not in the table above,
  because it doesn't bucket by month. It reads the last charge as **local** midnight
  (`new Date(lastDate + "T00:00:00")`), steps it forward with `setDate`, and compares it
  with the current **instant**. This can change a figure the user sees:
  - *Non-UTC machine vs production.* When the local date is behind UTC (evenings in New
    York), a charge due on the UTC date is still ahead of the local midnight it was parsed
    at. It shows as due in **0 days**. Production, on UTC, has already rolled it to the
    next cycle (**14 days** for a biweekly stream). Seen in the check below.
  - *Production on its own.* On a UTC host, any charge due today is behind "now" from
    00:00 UTC onward, so it rolls to the next cycle. The Upcoming list never shows a charge
    on the day it is due. This is not a local-dev artifact; it is live today.

  It sits alongside the subscriptionPriceUp remainder, but unlike that one it is visible.
  The fix is to compare UTC dates rather than instants. That is left for M7.6, which
  replaces this machinery, unless it is wanted sooner.

### Checked: can a non-UTC machine raise different alerts than production?

The M7.3 before/after report (`m7.3-reconciliation-part2.md`) found a Transportation
"pacing over budget" alert that appeared or disappeared with the clock. That came from the
**old** detector's local `getDate()`: the local day-of-month was 16 while the UTC money
period was on day 17. The question was whether the converted code still lets a laptop
disagree with Railway, which runs in UTC.

**Method.** A script loads the detector context for the demo user and runs all eight
detectors. It also collects every endpoint figure a user sees: insights, cash flow,
trends, month over month, the breakdown, budgets, score, digest and subscription streams.
The script ran under `TZ=UTC` and `TZ=America/New_York` on the local dev database, and the
two outputs were compared byte for byte. It ran at the real current time and with the
clock shifted to instants where the New York date is a day behind UTC:

| Instant (UTC) | New York date | Alerts raised | Output identical? |
|---|---|---|---|
| real time, evening of 09-16 New York | 09-16 (UTC 09-17) | 4 (incl. two budget pace alerts) | yes |
| 2026-09-01 02:30 (month boundary) | 08-31 | 3 | yes |
| 2026-08-01 03:30 (month boundary) | 07-31 | 3 | yes |
| 2026-09-10 02:30 (mid-period pace) | 09-09 | 6 (incl. **Transportation** pace) | alerts yes; **one figure no** |
| 2026-10-01 02:30, 11-01 03:30, 11-02 04:30 | previous day | 0–1 (after the data ends) | yes |
| 2026-03-09 03:30 (DST change) | 03-08 | 0 (before the data starts) | yes |

**Result.** Every alert, including its fingerprint and wording, matched at every instant.
The budget pace alert that moved in the report no longer depends on the machine's clock,
so the report's difference was a local-dev artifact of the old code. The one mismatch was
the `predictNextCharge` next-charge date above.

**Not exercised.** The seeded data runs from April to September, so no instant tested
both a daylight-saving change and live data. The `setDate` lookback windows (see "Not in
this class" above) and `missedPaycheck`'s windows are still unverified across DST. The
demo user raises no subscription price-change alert, so the subscriptionPriceUp
fingerprint remainder was not exercised either. It stays recorded on reading the code.

## Why this list outlives M7.3

M7.6 replaces the recurring and subscription machinery, and M7.5 adds card-cycle
budgets. Both need to know which parts of the app still hold private opinions about what
a transaction means. That is what this file is for: the conversion order below is a
snapshot, but the inventory is the map.
