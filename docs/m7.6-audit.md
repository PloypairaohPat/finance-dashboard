# M7.6 — recurring and subscriptions, Stage 0 audit

Audit only: no change to `src/` or the schema. Branched from `origin/main` at `4b73b525`.
Field names below are checked against the installed SDK, `plaid` 24.0.0
(`backend/node_modules/plaid/dist/api.d.ts`), not from memory.

## Part 1 — code

### 1. Who calls `/transactions/recurring/get`, and what they read

**One call site:** `fetchRecurring` in `backend/src/services/recurring.service.ts:6-84`. Per
Item it calls `transactionsRecurringGet({ access_token, account_ids })` (`:32`), keeps streams
whose `status` is `MATURE` or `EARLY_DETECTION` (`:40`, `:53`), and maps each to a new object:

| Raw field (SDK `TransactionStream`) | Mapped to |
|---|---|
| `merchant_name` / `description` | `merchantName` |
| `frequency` | `frequency` |
| `last_amount.amount` | `lastAmount` (absolute) |
| `average_amount.amount` | `averageAmount` (absolute) |
| `last_date` | `lastDate` |
| `status` | `status` |
| `personal_finance_category.primary` | `category` |

**Dropped:** `stream_id`, `account_id`, `first_date`, `transaction_ids`, `is_active`,
`is_user_modified`, `personal_finance_category.detailed`, and the response's
`updated_datetime`. The results are concatenated into `allOutflow` / `allInflow`, typed `any[]`
(`:23-24`), so nothing downstream is checked against this shape.

**Two readers of that output:**

- `GET /recurring` (`recurring.controller.ts:11`) returns it as-is. **Nothing in the frontend
  calls `/recurring`**; the endpoint is unused, but still calls Plaid for every Item on each hit.
- `plaidStreamsFor` (`subscriptions.service.ts:359-386`), the Plaid half of `GET /subscriptions`,
  reads the **raw** field names from the **mapped** objects:

| `plaidStreamsFor` reads | Exists on what it gets? | Effect |
|---|---|---|
| `s.is_active` (`:364`) | **No** (never mapped) | `undefined` → every stream skipped. This is why the Plaid half has never produced a stream. |
| `s.merchant_name` | **No** (`merchantName`) | would fall through |
| `s.description` | **No** | would fall through to `"Unknown"` |
| `s.personal_finance_category?.primary` | **No** (`category`) | would be `null` |
| `s.frequency` | yes | — |
| `s.last_amount?.amount` | **No** (`lastAmount`) | would be 0 |
| `s.last_date` | **No** (`lastDate`) | would be today |

**`predicted_next_date`:** the installed SDK's `TransactionStream` type **doesn't declare it**
(its fields: `account_id, stream_id, category, category_id, description, merchant_name,
first_date, last_date, frequency, transaction_ids, average_amount, last_amount, is_active,
status, personal_finance_category, is_user_modified, last_user_modified_datetime`). So it isn't
only the mapping that drops it: reading it needs a local type extension (or a newer SDK). Plaid's
JSON does carry it, on every stream (Part 2).

**Enums (SDK):** status `UNKNOWN | MATURE | EARLY_DETECTION | TOMBSTONED`; frequency
`UNKNOWN | WEEKLY | BIWEEKLY | SEMI_MONTHLY | MONTHLY | ANNUALLY`. The request's
`options.include_personal_finance_category` is deprecated: PFC is returned by default.

**Not rate-limited:** `plaidLimiter` (`app.ts:174-180`, 20 per 15 min) is applied only to
`/create_link_token`, `/create-update-link-token`, `/exchange_public_token` and `/sync`
(`app.ts:199-202`). `GET /recurring` and `GET /subscriptions` get the general limiter only, and
both call Plaid on every load.

**A failure risk worth knowing now:** `fetchSubscriptionAnalysis` awaits `plaidStreamsFor` with no
error handling (`subscriptions.service.ts:404`), and `fetchRecurring` lets a Plaid error throw. So
if Plaid refuses the call for an Item, `GET /subscriptions` answers 500 for that user, even though
the Plaid half contributes nothing. The first run saw no Plaid errors, so it isn't happening
today; PR 0 removes the risk.

### 3. `RECURRING_TRANSACTIONS_UPDATE`

**Today:** the webhook handler (`plaid.controller.ts:173-191`) acts only on `TRANSACTIONS` /
`SYNC_UPDATES_AVAILABLE`, `INITIAL_UPDATE`, `HISTORICAL_UPDATE` (it runs a sync) and on `ITEM`
errors. `RECURRING_TRANSACTIONS_UPDATE` is verified, logged, and ignored.

**From Plaid** (the SDK's endpoint and webhook documentation, which mirrors Plaid's API spec;
the docs site's page truncates before this section when fetched):

- The endpoint *"is offered as an add-on to Transactions. To request access to this endpoint,
  submit a product access request … or contact your Plaid account manager."* The docs site adds
  that Recurring Transactions is *"billed on a subscription model."* **Our client has it:** the
  script's first run got an answer from every Item, with no Plaid error (Part 2).
- *"This endpoint can only be called on an Item that has already been initialized with
  Transactions."* Plaid *"strongly recommend[s] … at least 180 days of history"* via
  `days_requested` at link time. Our `linkTokenCreate` didn't set it, so Items got Plaid's
  default of 90. **Done in PR 0b:** new links request 180 (`LINK_HISTORY_DAYS`). Existing Items
  keep what they had: it can't be changed once Transactions is on an Item.
- *"Once all historical transactions have been fetched, call `/transactions/recurring/get` to
  receive the Recurring Transactions streams and subscribe to the `RECURRING_TRANSACTIONS_UPDATE`
  webhook."* With `/transactions/sync`, history is complete when `SYNC_UPDATES_AVAILABLE` carries
  `historical_update_complete: true`.
- The webhook *"[f]ired when recurring transactions data is updated … when a new recurring stream
  is detected or when a new transaction is added to an existing recurring stream … [or] when one
  or more attributes of the recurring stream changes."* Payload: `item_id` and `account_ids`.

### 5. What a stored-streams table must join

**Built in PR 1** (`RecurringStream`, migration `20261006120100_recurring_streams`), with these

`PlaidItem` gains a unique `(id, userId)`.

| Place | What it does |
|---|---|
| Schema | `userId` → `User`, restrict on delete. Composite `(plaidItemId, userId)` → `PlaidItem(id, userId)`, restrict, so a stream's user is always its Item's owner; this needs `@@unique([id, userId])` on `PlaidItem`, as `Transaction` has for marks. ### 6. Where a dismiss denylist could key

Two events matter: **re-link** — today that means Reconnect (update mode), which keeps the Item,
or unlink-then-link, which makes a new Item — and **Plaid regrouping** a stream (splitting,
merging, or re-detecting it; a replaced stream shows up as `TOMBSTONED`).

| Key | Survives Reconnect | Survives unlink + link | Survives regrouping | Precision |
|---|---|---|---|---|
| Plaid `stream_id` | yes (same Item) | **no** — Plaid ids are per Item | **no** — a regrouped stream gets a new id | one stream |
| `merchantIdentity` | yes | yes (entity ids aren't per Item; the name fallback isn't either) | yes | **coarse:** dismissing one Apple subscription dismisses every Apple stream |
| An anchor transaction, like `SubscriptionMark` | yes | **no** (transactions are new) — the same as marks, tags and notes | yes: the series is re-derived on every read | one series |

**Recommendation: anchor on a transaction, like marks** — the same model, so the two can't
disagree, and precise where `merchantIdentity` is coarse. It loses dismissals on unlink + link,
which is already true of every other user-set state and is documented.

## Part 2 — script results

From `scripts/recurring-streams-audit.ts` against production (first run). Stated in relative
terms only: the repo is public, so no per-user stream counts or category breakdowns.

1. **Recurring Transactions is enabled.** Every Item answered `/transactions/recurring/get`
   with no Plaid error, so the gate in the original plan is dropped.
2. **Plaid's streams are a superset of subscriptions.** Most outflow streams are bills, loan
   payments and transfers. Putting them straight into the tab would fill it with rent and with
   transfers between a user's own accounts. Streams need sorting before anyone sees them.
3. **Every stream's transactions are in our rows.** So each stream can be judged by our own
   classifier, and a dismissal can anchor on a transaction, as §6 proposes.
4. **Most detector hits match a Plaid stream.** The one category where the detector finds
   something Plaid doesn't is Food & Dining — the kind of hit (a regular restaurant or café)
   the detector has always been prone to, along with groceries and gas.
5. **`predicted_next_date` is present on every stream**, despite the SDK type not declaring it.
   It is still read as nullable: Plaid's spec allows it to be absent.
6. **The "regular income" rule misfires.** Streams that pass "INCOME primary, mature, weekly to
   monthly" can be interest, not pay, while real pay can be irregular, coded as a transfer in,
   and form no stream at all. `INCOME` as a category primary isn't enough to call something a
   paycheck.

### Why the detector count can differ from what the Subscriptions tab shows

The script's "detected or marked" figure counts every stream the stored analysis returns — the
same list the tab draws — so a difference from the number of rows someone counts on the tab
comes from what the eye counts, not from a second source:

- **The tab has two lists.** Subscriptions and Bills are separate cards; the script counts both.
- **Ended marks are listed.** A marked subscription whose charges stopped stays in the list,
  labelled *Ended*, but out of the totals and Upcoming.
- **Lone charges are listed.** A mark on a single charge shows with *schedule unknown* and no
  monthly amount.
- **Upcoming is a third view of the same streams,** not more of them.
- **The window moves.** Detection reads the last 90 days at the moment it runs, so a stream near
  the edge can be in the script's run and gone by the next page load, or the other way round.

### Second run

The script also printed inflow streams by detailed category code and, for every stream, our
classifier's verdict on its transactions, by Plaid category primary.

1. **The interest reading is confirmed.** Every inflow stream the old heuristic called regular
   income is interest, except one, which is salary. The PR 6 rule — salary codes, a mature stream,
   a fixed frequency — selects exactly that one, across both users.
2. **Classifier-first is necessary on real data.** Card payments to a linked card come out as
   transfers; a payment to a card Ledger can't see comes out as spend (D3's proxy). Sorting on
   category alone would have listed linked-card payments as bills, double counting purchases that
   are already visible on the card.
3. **Every stream gets one verdict today:** none is mixed and none is unmatched. The definition
   still gives both a branch, so a future one can't fall through.

## Decisions

### Plaid's streams become the source; the custom detector retires

Two detectors that disagree is how M7.3's inconsistent numbers happened. So:

- **Stored Plaid streams are the source** of detected subscriptions and bills, sorted by the
  one definition below.
- **Marks cover what Plaid misses** — a gym under changing names, a stream Plaid hasn't formed.
  They keep their series walk; a mark and a stream that share a transaction are one subscription,
  shown as marked.
- **`detectCustomRecurring` is deleted** once streams reach the tab.
- **Price-up** reads the same composition: for a stream, its last two posted charges in our rows
  (through its `transaction_ids`); for a mark, its series, as now. It still waits for a pending
  charge to post, and still skips ended subscriptions.
- **The bell** keeps reading stored data only: stored streams + marks, never a Plaid call. The
  bell-is-a-subset-of-the-tab property holds by construction, as now.
- **The demo** seeds stream rows built from `demo-dataset.ts` instead of `demoRecurring()`: each
  fixture's charges become a stream whose `transaction_ids` are the demo's `plaidTransactionId`s.
  The price-rise fixture becomes a stream fixture; the marked gym stays a mark, showing what marks
  are for.

### One definition: subscription, bill, or not shown

Every stream is sorted once, in one function, before any surface sees it. Each branch is
explicit; there is no fall-through.

1. **Our classifier's verdict on the stream's transactions decides first.**

   | Verdict on its transactions | Result |
   |---|---|
   | all transfer (own accounts, card payments to a linked card, savings) | **not shown** |
   | all income | not a subscription or bill: inflows are PR 6's concern |
   | **mixed** (some spend, some not) | **not shown**, and counted in the refresh's log so a pattern can be spotted. Showing it would count its transfer charges as spending. |
   | **unmatched** (none of its transactions in our rows) | **not shown**: with no rows there's no verdict, no price-up and nothing to anchor a mark or dismissal on. It can show once its transactions sync. |
   | all spend | go to step 2 |

2. **All spend: then Plaid's category primary.**

   | Category primary | Result | Lands in, once shown |
   |---|---|---|
   | `RENT_AND_UTILITIES`, `LOAN_PAYMENTS` (including a payment to a card Ledger can't see) | **bill** | Bills |
   | `TRANSFER_OUT` | **needs confirmation** — a recurring payment the classifier counts as spending (a payment to a person, or to an account Ledger can't see), which may or may not be an obligation | **Bills**: a confirmed one is a recurring payment out, not a service |
   | `FOOD_AND_DRINK`, `GENERAL_MERCHANDISE`, `TRANSPORTATION` gas | **needs confirmation** — the detector's old false positives | Subscriptions |
   | anything else | **subscription** | Subscriptions |

   Confirming is a mark on one of the stream's charges; declining is a dismissal (PR 4). An
   unconfirmed stream is **suggested**: listed apart, outside every total, with Confirm and
   Dismiss (PR 5). Hiding it would leave nothing to confirm.

3. **Inactive** (`is_active: false`) → shown as **ended**, out of the totals.
4. **`UNKNOWN` frequency** → the existing unknown-schedule rule: listed, out of the totals.

### Inflows and `missedPaycheck`

PR 5 keys on salary codes (`INCOME_SALARY`; `INCOME_WAGES` where a v1 Item still sends it),
**never on the `INCOME` primary**. Interest (`INCOME_INTEREST_EARNED`) and dividends
(`INCOME_DIVIDENDS`) are excluded. It needs a `MATURE` stream with a fixed weekly-to-monthly
frequency, it is opt-in, and it is a state alert that resolves by absence. Someone paid
irregularly — no salary stream — never gets it, which is the M7.3 rule.

## Plan

Schema changes ship as two PRs: columns first, behaviour second.

- **PR 0 — stop calling Plaid on page load (no schema).** `GET /subscriptions` drops the Plaid
  half, which has never contributed a stream and can turn a Plaid refusal into a 500; the unused
  `GET /recurring` is deleted. No visible change except the 500 going away.
- **PR 0b — 180 days of history for new links.** `transactions.days_requested: 180` in
  `linkTokenCreate`, as Plaid recommends for Recurring Transactions. Only new links are
  affected; kept apart from PR 0 so PR 0 stays a pure removal.
- **PR 1 — columns: the stored-streams table, with every join in §5 in place**: the `User`
  foreign key (restrict) and the cascading `PlaidItem` one, the deletion service's order and the
  fingerprint's table list, unlink, the duplicate-link path, the inventory, and isolation tests
  with a stream fixture. Nothing writes a stream yet, so no real stream row can exist before the
  deletion path knows about the table.
- **PR 2 — fill and refresh it**, split per our rule:
  - **PR 2a — the refresh and the backfill, nothing calling the refresh automatically.**
    `src/services/recurringStreams.service.ts`: `fetchItemStreams` (one call, mapped, no writes),
    `planItemStreams` (what a refresh would do: the one definition) and `applyItemStreams`
    (executes the plan inside the transaction it's given). Only a successful response changes
    anything; an empty one clears the Item's streams; streams on accounts we don't hold are left
    out; the demo is refused. `scripts/backfill-recurring-streams.ts` fetches every non-demo Item
    first, then applies all of them in one transaction: dry run, then `--expect N`, with the
    count and a full-row fingerprint of everything outside `RecurringStream` checked before commit.
  - **One per-user lock** (`src/lib/userLock.ts`) is taken by apply, unlink and the
    duplicate-link discard (`removePlaidItemRows`), account deletion, and the link path. Before
    PR 2a only the link path took a lock; unlink and account deletion didn't. With restrict keys,
    a stream inserted while an Item is removed would fail the removal, possibly after Plaid had
    already removed it; now the second waits, and a refresh that finds its Item gone is a no-op.
  - **Reconciling the backfill's dry run with `recurring-streams-audit.ts`.** Both number users
    and Items the same way. The audit asked Plaid for the accounts we hold only (`account_ids`);
    the refresh asks for every account and leaves out the rest itself, so for each Item:
    *returned in + returned out − not our account = to write* in the backfill, and that equals the
    audit's *inflow + outflow* for the same Item, if Plaid's answer hasn't changed between runs.
    Any non-zero *not our account* is a stream the audit never saw.
  - **PR 2b-1 — `PlaidItem.streamsRefreshedAt`, no new triggers.** Set by `applyItemStreams` on
    every successful refresh (an empty one included) with raw SQL, so only that column changes —
    not the Item's `updatedAt`. The Plaid-items inventory shows it as an age ("3 h ago",
    "never"), never a date. Two checks it could have tripped, and one it showed was already
    fragile:
    - the recurring backfill's full-row check now leaves the column out, so a rerun doesn't abort;
    - the backfill and account deletion ran at READ COMMITTED, so **another user's commit between
      their two fingerprints aborted them** — reproduced by a test before the fix. Both now run at
      REPEATABLE READ, one snapshot for both fingerprints. The demo reseed already did, and its
      fingerprint is ids only, so a stamp never touches it.
  - **PR 2b-2 — call it:** on **`RECURRING_TRANSACTIONS_UPDATE`** (that Item only), a **daily
    backstop** for Items not refreshed in 20 hours (our Items have pointed at a dead webhook URL
    before), and the first refresh for a new link when `SYNC_UPDATES_AVAILABLE` arrives with
    `historical_update_complete: true` and `streamsRefreshedAt` is still empty. That first refresh
    runs **after the sync the same webhook starts**, not alongside it, so the stream's
    transactions are already in our rows when it lands. **Never on page load.**
    **Built:** `refreshOnRecurringUpdate`, `firstRefreshIfNeeded` and `refreshStaleItems` in
    `recurringStreams.service.ts`, each reporting its own failures and never throwing; the
    webhook handler verifies, answers Plaid, then calls them; the backstop runs at 07:00 UTC, an
    hour after the 06:00 sync. Items with an empty stamp (all of them, after PR 2b-1) get their
    first refresh from whichever comes first: a `SYNC_UPDATES_AVAILABLE` carrying
    `historical_update_complete`, or the backstop.
  - `predicted_next_date` through a **local nullable type**. Upgrading `plaid` is a separate
    chore PR.
  - Streams are stored but not yet shown.
- **PR 3 — the one definition** (above), tested on its own: stream → subscription, bill, needs
  confirmation, or not shown. Still nothing in the UI.
  **Built:** `sortStream` in `src/lib/streamSorting.ts` (pure) gives each stream a bucket
  (subscription, bill, suggested, hidden), a reason code, whether it counts toward totals
  (a subscription or bill, active, known frequency) and, if suggested, where it lands once
  confirmed. `sortUserStreams` resolves transaction ids to the stream's own user's live rows
  and classifies them. `scripts/stream-sorting-audit.ts` prints the result as counts. Changes
  from the table above, agreed for PR 3:
  - "Needs confirmation" is its own bucket, **suggested**.
  - **Status decides before category.** Plaid documents four statuses and none means merged or
    split (those are operations an app calls; Ledger calls neither). A value outside the four is
    hidden; `TOMBSTONED` (an early stream that didn't recur) is hidden; `EARLY_DETECTION` and
    `UNKNOWN` are suggested whatever the category. Transfers stay hidden whatever the status.
  - **Categories are matched on PFCv2 codes, detailed before primary:** bills also include
    `BANK_FEES`, `GENERAL_SERVICES_INSURANCE` and `GOVERNMENT_AND_NON_PROFIT_TAX_PAYMENT`; gas is
    `TRANSPORTATION_GAS` only; subscriptions are an explicit list of detailed codes (TV and
    movies, music and audio, video games, gyms, storage).
  - **A spend stream on neither list is suggested,** not a subscription: a false subscription
    costs more trust than one extra confirm.
  - The refresh does not yet log mixed streams; the audit script counts them.
- **PR 4 — columns: dismissals**, anchored on a transaction (a `kind` on `SubscriptionMark`, or
  a sibling table).
  **Built:** `SubscriptionMark.kind`, a `MarkKind` enum (`confirmed`, `dismissed`), default
  `confirmed`, so existing marks read as confirmations. The existing one-row-per-charge key means
  a charge is confirmed or dismissed, never both; the existing foreign key anchors a dismissal to
  its user's transaction as it does a mark. Where a confirmation lands (Subscriptions or Bills)
  isn't stored: it follows the sorting definition's `confirmsAs` on every read. Everything that
  reads marks today reads confirmations only (the tab's analysis, membership, un-mark, the
  create path), so a dismissal can never show as a subscription. No code writes a dismissal yet.
  Also on this branch: a suggested stream that is inactive is hidden (`ended-unconfirmed`).
  **For PR 5,** now that a confirmation can be a bill:
  - The analysis builds every mark as a subscription (`subscriptions.service`, one stream per
    mark): a confirmed stream whose `confirmsAs` is a bill must land in Bills, and a mark on a
    charge with no stream stays a subscription.
  - Labels: "Mark as subscription", "Marked as a subscription · Unmark" and its help text
    (`TransactionDetail.tsx`), "Marked by you" and its tooltip (`SubscriptionTracker.tsx`), and
    membership's `marked` state (`types.ts`) all assume a subscription. Confirm and Dismiss on
    the suggested list need their own wording, and so does undoing a dismissal.
  - The user doc (`what-changed-for-you.md`, "You can mark a subscription yourself") describes
    marks as subscriptions only; it needs confirm, dismiss and bills.
  - Price-up and the bell read the analysis, so they follow whatever it does with bills; the
    duplicate and price-change rules skip marks today and need the same check for confirmed
    bills.
  - The create path's duplicate fallback finds a confirmation only; confirming a dismissed
    charge must decide whether it replaces the dismissal (one row per charge).
- **PR 5 — behaviour: streams reach the tab and the bell.** The composition above; confirm and
  dismiss; price-up and the bell on the new source; the demo's stream fixtures; the custom
  detector deleted. Split so that each part deploys on its own and the tab never double counts:
  only 5e changes what the tab and the bell read.
  - **5a — composition, unwired.** `composeSubscriptions` (`streamComposition.service.ts`):
    the sorting plus verdicts. A stream's verdict is the latest on any of its charges (covers
    Plaid regrouping). Confirmed: shown in its bucket, or `confirmsAs` for a suggestion, counted
    when active with a known frequency, shown as ended when inactive (overriding
    `ended-unconfirmed`). Dismissed: not shown, listed under `dismissed` with the dismissal id
    for Restore. A confirmation on a charge in no stream, or only in a stream the sorting hides
    for another reason, is walked as a series, as today. No charge shows twice: confirmed
    streams claim their charges first, then marked series, then other streams, then
    suggestions; an item reaching a claimed charge folds into the one that has it (the gym).
    **Monthly amount** (`lib/monthlyAmount.ts`), by what the number means: a subscription's last
