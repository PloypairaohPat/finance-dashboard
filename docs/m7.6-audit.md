# M7.6 — recurring and subscriptions, Stage 0 audit

Audit only: no change to `src/` or the schema. Branched from `origin/main` at `4b73b525`.
Field names below are checked against the installed SDK, `plaid` 24.0.0

## Part 1 — code

### 1. Who calls `/transactions/recurring/get`, and what they read

**One call site:** `fetchRecurring` in `backend/src/services/recurring.service.ts:6-84`. Per
Item it calls `transactionsRecurringGet({ access_token, account_ids })` (`:32`), keeps streams
whose `status` is `MATURE` or `EARLY_DETECTION` (`:40`, `:53`), and maps each to a new object:

| Raw field (SDK `TransactionStream`) | Mapped to |
|---|---|
| `merchant_name` / `description` | `merchantName` |
| `frequency` | `frequency` |
| `last_amount.amount` | `lastAmount` (absolute) |
| `average_amount.amount` | `averageAmount` (absolute) |
| `last_date` | `lastDate` |
| `status` | `status` |
| `personal_finance_category.primary` | `category` |

**Dropped:** `stream_id`, `account_id`, `first_date`, `transaction_ids`, `is_active`,
`is_user_modified`, `personal_finance_category.detailed`, and the response's
`updated_datetime`. The results are concatenated into `allOutflow` / `allInflow`, typed `any[]`
(`:23-24`), so nothing downstream is checked against this shape.

**Two readers of that output:**

- `GET /recurring` (`recurring.controller.ts:11`) returns it as-is. **Nothing in the frontend
  calls `/recurring`**; the endpoint is unused, but still calls Plaid for every Item on each hit.
- `plaidStreamsFor` (`subscriptions.service.ts:359-386`), the Plaid half of `GET /subscriptions`,
  reads the **raw** field names from the **mapped** objects:

| `plaidStreamsFor` reads | Exists on what it gets? | Effect |
|---|---|---|
| `s.is_active` (`:364`) | **No** (never mapped) | `undefined` → every stream skipped. This is why the Plaid half has never produced a stream. |
| `s.merchant_name` | **No** (`merchantName`) | would fall through |
| `s.description` | **No** | would fall through to `"Unknown"` |
| `s.personal_finance_category?.primary` | **No** (`category`) | would be `null` |
| `s.frequency` | yes | — |
| `s.last_amount?.amount` | **No** (`lastAmount`) | would be 0 |
| `s.last_date` | **No** (`lastDate`) | would be today |

**`predicted_next_date`:** the installed SDK's `TransactionStream` type **doesn't declare it**
(its fields: `account_id, stream_id, category, category_id, description, merchant_name,
first_date, last_date, frequency, transaction_ids, average_amount, last_amount, is_active,
status, personal_finance_category, is_user_modified, last_user_modified_datetime`). So it isn't
only the mapping that drops it: reading it needs a newer SDK or a local type extension. The
script reports whether Plaid's JSON carries the key.

**Enums (SDK):** status `UNKNOWN | MATURE | EARLY_DETECTION | TOMBSTONED`; frequency
`UNKNOWN | WEEKLY | BIWEEKLY | SEMI_MONTHLY | MONTHLY | ANNUALLY`. The request's
`options.include_personal_finance_category` is deprecated: PFC is returned by default.

**Not rate-limited:** `plaidLimiter` (`app.ts:174-180`, 20 per 15 min) is applied only to
`/create_link_token`, `/create-update-link-token`, `/exchange_public_token` and `/sync`
(`app.ts:199-202`). `GET /recurring` and `GET /subscriptions` get the general limiter only, and
both call Plaid on every load.

**A failure risk worth knowing now:** `fetchSubscriptionAnalysis` awaits `plaidStreamsFor` with no
error handling (`subscriptions.service.ts:404`), and `fetchRecurring` lets a Plaid error throw. So
if Plaid refuses the call for an Item, `GET /subscriptions` answers 500 for that user, even though
the Plaid half contributes nothing. The script's error codes say whether that is happening.

### 2. Where each surface gets its data

| Surface | Source |
|---|---|
| Subscriptions tab | `GET /subscriptions` → `fetchSubscriptionAnalysis` (`:397`) = stored streams + the Plaid half (always empty) |
| Stored streams | `storedStreams` (`:343`): **marks** (`markedStreams`, `:293`) + the **custom detector** (`detectCustomRecurring`, `:96`) over 90 days of classifier spend, grouped by `merchantIdentity`; a detected stream sharing a charge with a mark is dropped |
| The bell | `loadContext` → `analyseStoredSubscriptions` (`dispatcher.ts:59`): the same stored streams, never Plaid |
| Price-up | `detectSubscriptionPriceUp` over the bell's analysis: price changes from the detector (latest vs previous charge per identity) and from marks (their own series); waits for a pending charge to post; skips ended marks |
| `GET /recurring` | Plaid, mapped (above); unused |

Every subscription anyone has seen came from the custom detector or a mark.

### 3. `RECURRING_TRANSACTIONS_UPDATE`

**Today:** the webhook handler (`plaid.controller.ts:173-191`) acts only on `TRANSACTIONS` /
`SYNC_UPDATES_AVAILABLE`, `INITIAL_UPDATE`, `HISTORICAL_UPDATE` (it runs a sync) and on `ITEM`
errors. `RECURRING_TRANSACTIONS_UPDATE` is verified, logged, and ignored.

**From Plaid** (the SDK's endpoint and webhook documentation, which mirrors Plaid's API spec;
the docs site's page truncates before this section when fetched):

- The endpoint *"is offered as an add-on to Transactions. To request access to this endpoint,
  submit a product access request … or contact your Plaid account manager."* The docs site adds
  that Recurring Transactions is *"billed on a subscription model."* **Whether our client has
  it is unknown** — Balance turned out not to be authorised. The script answers this first.
- *"This endpoint can only be called on an Item that has already been initialized with
  Transactions."* Plaid *"strongly recommend[s] … at least 180 days of history"* via
  `days_requested` at link time. **Our `linkTokenCreate` doesn't set `days_requested`**
  (`plaid.service.ts:24-31`), so Items get Plaid's default.
- *"Once all historical transactions have been fetched, call `/transactions/recurring/get` to
  receive the Recurring Transactions streams and subscribe to the `RECURRING_TRANSACTIONS_UPDATE`
  webhook."* With `/transactions/sync`, history is complete when `SYNC_UPDATES_AVAILABLE` carries
  `historical_update_complete: true`.
- The webhook *"[f]ired when recurring transactions data is updated … when a new recurring stream
  is detected or when a new transaction is added to an existing recurring stream … [or] when one
  or more attributes of the recurring stream changes."* Payload: `item_id` and `account_ids`.

### 6. Where a dismiss denylist could key

Two events matter: **re-link** — today that means Reconnect (update mode), which keeps the Item,
or unlink-then-link, which makes a new Item — and **Plaid regrouping** a stream (splitting,
merging, or re-detecting it; a replaced stream shows up as `TOMBSTONED`).

| Key | Survives Reconnect | Survives unlink + link | Survives regrouping | Precision |
|---|---|---|---|---|
| Plaid `stream_id` | yes (same Item) | **no** — Plaid ids are per Item | **no** — a regrouped stream gets a new id | one stream |
| `merchantIdentity` | yes | yes (entity ids aren't per Item; the name fallback isn't either) | yes | **coarse:** dismissing one Apple subscription dismisses every Apple stream |
| An anchor transaction, like `SubscriptionMark` | yes | **no** (transactions are new) — the same as marks, tags and notes | yes: the series is re-derived on every read | one series |

**Recommendation: anchor on a transaction, like marks** — the same model, so the two can't
disagree, and precise where `merchantIdentity` is coarse. It loses dismissals on unlink + link,
which is already true of every other user-set state and is documented.

## Proposed plan

Gate first: **if the script shows Recurring Transactions isn't authorised** (an
`INVALID_PRODUCT`-style error on every Item), the stored-streams half needs a product access
request and a cost decision before anything below PR 0.

- **PR 0 — stop calling Plaid on page load (no schema).** `GET /subscriptions` drops the Plaid
  half (it has never contributed a stream, and can turn a Plaid refusal into a 500); delete the
  unused `GET /recurring`. No visible change except the 500 going away.
- **PR 1 — columns: the stored-streams table.** Schema, FKs, and every join in §5. No behaviour.
- **PR 2 — behaviour: fetch and store streams.** Typed mapping (including
  `predicted_next_date`, via an SDK upgrade or a local type), called when history completes
  (`historical_update_complete`) and on `RECURRING_TRANSACTIONS_UPDATE` — never on page load.
  `days_requested: 180` for new links. The tab and the bell compose stored Plaid streams, the
  detector and marks, merged by shared transactions; the bell stays a subset of the tab.
- **PR 3 — columns: dismissals.** Either a `kind` on `SubscriptionMark` or a sibling table,
  anchored on a transaction (§6).
- **PR 4 — behaviour: dismiss, and detector noise.** The dismiss action; groceries, coffee and
  gas suppressed — by Plaid's streams where they exist, and by category where they don't.
- **PR 5 — `missedPaycheck` returns** on stored inflow streams only: `MATURE`, a fixed weekly to
  monthly frequency, an `INCOME` category, opt-in, a state alert that resolves by absence, and
  never on an irregular stream (the M7.3 notes in `docs/m7.3-consumer-audit.md`).
