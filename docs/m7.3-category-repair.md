# Rows saved with a display name: count, then repair

Before the category-save fix, `PATCH /transactions/:id` stored the chosen **display name**
("Shopping") in `categoryPrimary`, where Plaid codes live. The fix stops new ones. Rows
already written that way are still wrong in production. This file covers the read-only
count and a proposed repair. **Neither has been run.** The repair is a data migration and
needs a decision first.

## How the damage shows

`mapPlaidCategory` upper-cases the stored value and matches by prefix. So:

| Stored | Counted under | Right? |
|---|---|---|
| `Transportation`, `Travel`, `Entertainment` | the same name, because the prefix happens to match | yes, by accident |
| `Housing`, `Food & Dining`, `Shopping`, `Bills & Utilities`, `Debt`, `Subscriptions`, `Other` | **Other** | no |

The row's verdict can also have changed, because the edit replaced a `TRANSFER_*` or
`INCOME*` primary. For example, an income deposit recategorised to Shopping stops being
income and becomes an unidentified inflow.

Plaid codes are upper-case and display names are not, so an exact, case-sensitive match
on the ten names cannot catch a genuine Plaid code.

## 1. Counts only (read-only, returns no identifiers or amounts)

```sql
SELECT
  t."categoryPrimary"                                         AS stored_display_name,
  CASE
    WHEN t."rawJson"->'personal_finance_category'->>'detailed' LIKE 'TRANSFER\_%'
      OR t."rawJson"->'personal_finance_category'->>'primary'  LIKE 'INCOME%'
      OR t."rawJson"->'personal_finance_category'->>'detailed' = 'LOAN_PAYMENTS_CREDIT_CARD_PAYMENT'
      OR t."categoryPrimary" = 'Subscriptions'
    THEN 'restore Plaid codes'
    WHEN t."rawJson" IS NULL THEN 'assign codes (no Plaid original)'
    ELSE 'assign codes'
  END                                                         AS proposed_action,
  count(*)                                                    AS rows,
  count(DISTINCT t."userId")                                  AS users,
  count(*) FILTER (WHERE t."deletedAt" IS NULL)               AS live_rows
FROM "Transaction" t
WHERE t."categoryPrimary" IN (
  'Housing', 'Food & Dining', 'Shopping', 'Transportation', 'Bills & Utilities',
  'Subscriptions', 'Entertainment', 'Travel', 'Debt', 'Other'
)
GROUP BY 1, 2
ORDER BY 1, 2;
```

If this returns no rows, there is nothing to repair and section 2 can be dropped.

## 2. Proposed repair (NOT applied)

There are two cases, matching the rule the fix now enforces (`canRecategorise`):

- **Restore Plaid's codes from `rawJson`.** This applies where the original row was a
  transfer, income, or a card payment. The new rule would have refused that edit, and
  keeping it would leave a verdict changed. It also applies to `Subscriptions`, which no
  code represents.
- **Assign the codes for the name the user chose.** This covers every other row. It keeps
  the user's intent, stored the way the fix now stores it
  (`ASSIGNABLE_CATEGORY_CODES`).

```sql
BEGIN;

-- (a) Edits the new rule would refuse: put Plaid's original codes back.
UPDATE "Transaction" t
SET "categoryPrimary"  = t."rawJson"->'personal_finance_category'->>'primary',
    "categoryDetailed" = t."rawJson"->'personal_finance_category'->>'detailed'
WHERE t."categoryPrimary" IN ('Housing','Food & Dining','Shopping','Transportation',
        'Bills & Utilities','Subscriptions','Entertainment','Travel','Debt','Other')
  AND t."rawJson" IS NOT NULL
  AND (   t."rawJson"->'personal_finance_category'->>'detailed' LIKE 'TRANSFER\_%'
       OR t."rawJson"->'personal_finance_category'->>'primary'  LIKE 'INCOME%'
       OR t."rawJson"->'personal_finance_category'->>'detailed' = 'LOAN_PAYMENTS_CREDIT_CARD_PAYMENT'
       OR t."categoryPrimary" = 'Subscriptions');

-- (b) Everything else: store the chosen category as its codes.
UPDATE "Transaction" t
SET "categoryPrimary" = m.primary_code, "categoryDetailed" = m.detailed_code
FROM (VALUES
  ('Housing',           'HOME_IMPROVEMENT',    'HOME_IMPROVEMENT_OTHER_HOME_IMPROVEMENT'),
  ('Food & Dining',     'FOOD_AND_DRINK',      'FOOD_AND_DRINK_OTHER_FOOD_AND_DRINK'),
  ('Shopping',          'GENERAL_MERCHANDISE', 'GENERAL_MERCHANDISE_OTHER_GENERAL_MERCHANDISE'),
  ('Transportation',    'TRANSPORTATION',      'TRANSPORTATION_OTHER_TRANSPORTATION'),
  ('Bills & Utilities', 'RENT_AND_UTILITIES',  'RENT_AND_UTILITIES_OTHER_UTILITIES'),
  ('Entertainment',     'ENTERTAINMENT',       'ENTERTAINMENT_OTHER_ENTERTAINMENT'),
  ('Travel',            'TRAVEL',              'TRAVEL_OTHER_TRAVEL'),
  ('Debt',              'LOAN_PAYMENTS',       'LOAN_PAYMENTS_OTHER_PAYMENT'),
  ('Other',             NULL,                  NULL)
) AS m(display_name, primary_code, detailed_code)
WHERE t."categoryPrimary" = m.display_name;

-- Re-run the counts query: it must now return no rows.
-- A 'Subscriptions' row with no rawJson survives both steps and shows up here.
COMMIT;
```

Before applying:

- Run the counts query and read the sizes. A large *restore* group means real people moved
  transfers or income, and the "keep their intent" argument for those rows deserves a look
  before it is overridden.
- Run it against a restored copy of production first, and diff `verify-figures` before and
  after for the affected users.
- The mapping in (b) must match `ASSIGNABLE_CATEGORY_CODES`. The test
  `transactions-recategorise.test.ts` pins that table, so change both together or neither.
