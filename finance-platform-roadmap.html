Tech Stack

Every tool chosen for a reason — cheap to run now, scales without rewrites later. Tools in green are for immediate use. Amber means add in a later phase.

Much faster to iterate on UI. No context-switching between files. Works great with component-based React. The utility classes become second nature within a week.
Type safety Add in Phase 2
TypeScript
Add to both frontend + backend together
Don't add it right now — you have enough to build. Add it in Phase 2 when the schema is stable. TypeScript on a stable codebase is much less painful than retrofitting a moving one.

Backend

Server Keep
Node.js + Express
No reason to change
You already have it. The real upgrade is your folder structure — move from a single server.js to a routes/controllers/services/repositories pattern (see Architecture section).
ORM Add now
Prisma
Alternative: Drizzle (lighter)
Type-safe database client + automatic migration system. You define your schema in schema.prisma and it generates migrations. Beats writing raw SQL for CRUD. Critical when you add TypeScript.
Validation Add now

Used for request + env validation
Validate all incoming API request bodies and your .env variables at startup. Catches bugs like missing fields and bad types before they reach the database.
Caching Add in Phase 3
Redis
Only add when you actually need it
Cache expensive aggregation queries (monthly summaries, category totals). Don't add this now — PostgreSQL is fast enough for a single-user app. Add when queries start taking >500ms.

Phased Roadmap

Built around your constraints: student budget, currently single-user, wants to avoid both overengineering and costly rewrites. Each phase has a clear exit condition before moving on.

Foundation
Database · Webhooks · Dashboard UI
Now → 8 weeks

The goal of Phase 1 is simple: make the app real. Replace all temporary solutions (in-memory storage, no webhooks, no UI) with production-grade foundations. Don't add anything else until this is done.

  • Week 4–5: Spending dashboard. Build the category summary endpoint. Add a Recharts donut chart to the React frontend. This is the first UI milestone that makes the app feel like a product. do now
  • Week 5–6: Transaction search & filtering. Pure frontend work — filter the in-state transaction array by date, merchant, amount. Debounce the text input. Add sort toggles. do now
  • Week 6–7: Recurring detection. Add /recurring endpoint using plaidClient.transactionsRecurringGet(). Display subscriptions + income streams in a separate card. do now
  • Week 7–8: Deploy to Vercel + Railway + Supabase. Get the app live. Use environment variables for all secrets. Add basic error logging (console is fine, add Sentry later). do now
  • Multi-user auth — SKIP. Design the DB schema with user_id on every table (see Architecture), but don't build login flows. A single hardcoded user is fine for now. skip for now

ML & Automation
Forecasting · Anomaly detection · Pipelines
Month 4–8

You now have 4+ months of clean historical data. This is when ML becomes viable — you need data history before you can forecast anything meaningfully. Don't attempt this phase early.

  • Spending forecast (Prophet). Use Facebook Prophet on your monthly category totals. Predict next month's spending per category. This requires ~3 months of data to be useful. Serve predictions via a Python FastAPI endpoint.
  • Anomaly detection. Flag transactions that are outliers for their merchant/category (e.g. unusually large grocery spend). Start with simple IQR-based detection, upgrade to Isolation Forest if needed.

  • Add Redis for caching. Cache expensive aggregation queries (monthly summary, trend data) that don't change until the next sync. Only add this if queries are noticeably slow. only if needed

System Architecture

Designed for one user today, ten users tomorrow — without changing a single database column. The key decision: put user_id on every table from Day 1, even when there's only one user.

Backend folder structure

Refactor server.js into this layout at the start of Phase 2. Each layer has one job:

# Current (everything in server.js) — works, but won't scale
backend/
  server.js         # 400+ lines, routes + logic + DB all mixed

# Target structure (Phase 2+)
backend/
  src/
    routes/         # Express route definitions only — just app.get/post
      plaid.js      # /create_link_token, /exchange_public_token
      transactions.js
      accounts.js
      analytics.js
    controllers/    # Thin — parse req, call service, send res
      plaid.controller.js
      transactions.controller.js
    services/       # All business logic lives here
      plaid.service.js     # token exchange, webhook handling
      sync.service.js      # /transactions/sync logic + cursor management
      analytics.service.js # category summaries, trend calculations
    repositories/   # All database queries — ONLY place Prisma is called
      transaction.repo.js
      account.repo.js
      plaid.repo.js
    jobs/           # Cron jobs + webhook handlers
      daily-sync.job.js
      webhook.handler.js
    middleware/
      error.middleware.js
      auth.middleware.js   # stub now, real later
    utils/
      plaid.client.js  # singleton Plaid client (move out of server.js)
      encrypt.js       # for access token encryption
  prisma/
    schema.prisma
    migrations/
  .env
The rule: Routes call controllers. Controllers call services. Services call repositories. Repositories call Prisma. Nothing skips a layer. This means you can change the database by only touching the repository files.

Database schema

The critical design decision: user_id on every table, populated with a single hardcoded ID for now. When you add real auth, you just wire in the real user ID — zero schema changes.

-- ─── schema.prisma (Prisma ORM syntax) ──────────────────────────

-- Single user for now, but every table is multi-user ready.
-- Seed a single user row on startup: id='user_default'

model User {
  id          String       @id @default(cuid())
  email       String?      @unique
  createdAt   DateTime     @default(now())
  plaidItems  PlaidItem[]
  accounts    Account[]
  transactions Transaction[]
  budgets     Budget[]
}

model PlaidItem {
  id              String    @id @default(cuid())
  userId          String    -- always present, even for single user
  user            User      @relation(fields: [userId], references: [id])
  accessToken     String    -- store encrypted! (AES-256)
  itemId          String    @unique
  institutionName String?
  cursor          String?   -- for /transactions/sync pagination
  createdAt       DateTime  @default(now())
  accounts        Account[]
}

model Account {
  id              String    @id @default(cuid())
  userId          String
  user            User      @relation(fields: [userId], references: [id])
  plaidItemId     String
  plaidItem       PlaidItem @relation(fields: [plaidItemId], references: [id])
  plaidAccountId  String    @unique
  name            String
  officialName    String?
  type            String    -- depository | credit | investment
  subtype         String?   -- checking | savings | credit card
  mask            String?   -- last 4 digits
  transactions    Transaction[]
}

model Transaction {
  id                  String    @id @default(cuid())
  userId              String
  user                User      @relation(fields: [userId], references: [id])
  accountId           String
  account             Account   @relation(fields: [accountId], references: [id])
  plaidTransactionId  String    @unique
  date                DateTime
  amount              Decimal   -- positive = debit, negative = credit
  name                String    -- raw Plaid name
  merchantName        String?   -- cleaned merchant (may be null)
  categoryPrimary     String?   -- FOOD_AND_DRINK, TRANSPORTATION, etc.
  categoryDetailed    String?
  pending             Boolean   @default(false)
  rawJson             Json      -- full Plaid response, immutable, for ML
  createdAt           DateTime  @default(now())

  -- Indexes — critical for query performance
  @@index([userId, date])
  @@index([userId, categoryPrimary])
  @@index([accountId, date])
}

model Budget {
  id              String    @id @default(cuid())
  userId          String
  user            User      @relation(fields: [userId], references: [id])
  category        String    -- matches categoryPrimary
  monthlyLimit    Decimal
  createdAt       DateTime  @default(now())
}

model SyncLog {
  id          String    @id @default(cuid())
  userId      String
  itemId      String
  status      String    -- success | error
  addedCount  Int
  modifiedCount Int
  removedCount  Int
  errorMessage  String?
  createdAt   DateTime  @default(now())
}

Best Practices

The decisions you make in Phase 1 are the hardest to undo in Phase 3. These practices cost almost nothing now and save weeks of refactoring later.

🗄
Database design
  • ✓ user_id on every table — even with one user. Populate with a default user row.
  • ✓ Never hard-delete transactions. Use a deletedAt nullable timestamp.
  • ✓ Store Plaid's raw JSON in a rawJson column. It's your source of truth and future training data.
  • ✓ Add indexes on (userId, date) and (userId, categoryPrimary) from day one.
  • ✓ Use Decimal (not Float) for all monetary amounts. Floats cause rounding errors.
  • ✓ Store all timestamps in UTC. Display conversion is the frontend's job.
🔄
Migrations — never edit schema directly
  • ✓ Always run npx prisma migrate dev to create a migration file. Never hand-edit the DB.
  • ✓ Every schema change = one migration file = one git commit.
  • ✓ Name migrations descriptively: add_cursor_to_plaid_items, not migration_v2.
  • ✓ Test migrations on a copy of production data before applying to prod.
  • ✓ Never delete old migration files — they're your history.
🔐
Security basics
  • ✓ Encrypt Plaid access tokens at rest before storing. Use AES-256 with a key in .env.
  • ✓ Never log access tokens, even to console. Scrub them from error logs.
  • ✓ Validate Plaid webhook signatures — never skip this. It prevents spoofed webhooks.
  • ✓ Use Zod to validate every incoming request body. Reject malformed input early.
  • ✓ .env is in .gitignore. Use .env.example with placeholder values in git.
📊
Data pipeline design
  • ✓ Raw data is immutable. Never UPDATE or DELETE a rawJson value once stored.
  • ✓ All pipelines must be idempotent — running twice produces the same result.
  • ✓ Log every sync run to a sync_logs table: rows added, modified, removed, errors.
  • ✓ Use Plaid's cursor (from /transactions/sync) to avoid re-fetching everything. Store cursor per item in the DB.
  • ✓ Separate raw → cleaned → aggregated layers. Never mix them.
🏗
Avoiding technical debt
  • ✓ Add TypeScript in Phase 2 — don't wait until Phase 3 when there's 5,000 lines to convert.
  • ✓ Don't add Redis, message queues, or microservices until you've profiled and confirmed you need them.
  • ✓ Keep Python and Node.js strictly separated — don't try to run Python from Node via child_process.
  • ✓ Refactor server.js into the routes/controllers/services/repos structure at the start of Phase 2, not later.
  • ✓ Write a README for every service that explains how to run it locally. Future you will thank present you.
🧪
Testing strategy (minimal but effective)
  • ✓ Don't write unit tests for everything — too slow for a solo dev. Focus on integration tests for critical paths.
  • ✓ Test: token exchange flow, webhook handler, transaction sync, category aggregation.
  • ✓ Use Vitest (fast, works with Vite) for backend. It's Jest-compatible so docs apply.
  • ✓ Use a test PostgreSQL database (separate Docker container) for integration tests.
  • ✓ Plaid sandbox has test credentials (user_good, pass_good) — write end-to-end tests against it.

The one rule that pays off most

Keep raw data immutable and separated from derived data. Your transactions table has a rawJson column containing the exact Plaid response. You never touch this column after insert. All cleaning, normalization, and ML features are derived from it into separate columns and tables. In 2 years when you want to retrain an ML model with better features, you still have all the original data. This decision costs you a few extra megabytes of storage and saves you months of regret.

Secrets and access token encryption

// utils/encrypt.js — AES-256-GCM encryption for access tokens
const crypto = require('crypto')
const KEY = Buffer.from(process.env.ENCRYPTION_KEY, 'hex') // 32-byte key

function encrypt(text) {
  const iv = crypto.randomBytes(12)
  const cipher = crypto.createCipheriv('aes-256-gcm', KEY, iv)
  const encrypted = Buffer.concat([cipher.update(text, 'utf8'), cipher.final()])
  const tag = cipher.getAuthTag()
  return [iv, tag, encrypted].map(b => b.toString('base64')).join('.')
}

function decrypt(str) {
  const [iv, tag, encrypted] = str.split('.').map(s => Buffer.from(s, 'base64'))
  const decipher = crypto.createDecipheriv('aes-256-gcm', KEY, iv)
  decipher.setAuthTag(tag)
  return decipher.update(encrypted) + decipher.final('utf8')
}

// Generate your ENCRYPTION_KEY once:
// node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
